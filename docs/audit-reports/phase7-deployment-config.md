## Executive Summary

Zero dependency vulnerabilities across both mobile and admin apps. The core Expo/EAS configuration is solid — correct bundle IDs, proper SDK alignment, appropriate permissions. However, several **store-blocking** issues exist: EAS submit config contains placeholder Apple IDs, Android release builds use the debug keystore, and the Supabase auth config has weak password settings (minimum 6, no complexity). No CI/CD pipelines exist. The `.env.local.example` files are incomplete (missing `MAPBOX_DOWNLOAD_TOKEN`) and inconsistent between mobile and admin. Several Expo packages have minor patch updates available within the SDK 55 range.

**Totals:** 14 findings — 5 to fix now, 6 noted (manual/process steps), 3 informational

## Findings

### P7-001 | CRITICAL | EAS submit config has placeholder Apple IDs

**File:** `eas.json` (lines 26-29)

```json
"ios": {
  "ascAppId": "YOUR_APP_STORE_CONNECT_APP_ID",
  "appleTeamId": "YOUR_APPLE_TEAM_ID"
}
```

`eas submit` will fail with these placeholder values. This blocks iOS App Store submission entirely.

**Impact:** iOS store submission blocked
**Fix:** Replace with real values after Apple Developer enrollment (documented in store-launch-checklist.md). No code fix — manual process step.
**Status:** NOTED — Requires Apple Developer Program enrollment. Already tracked in store-launch-checklist.md.

### P7-002 | CRITICAL | Android release signing uses debug keystore

**File:** `android/app/build.gradle` (line ~67)

```groovy
release {
    signingConfig signingConfigs.debug
}
```

Release APKs/AABs signed with the debug keystore will be rejected by Google Play. However, `android/` is fully gitignored and regenerated by `expo prebuild` — EAS Build handles signing via credentials configured in Expo's credential manager.

**Impact:** Only affects local `./gradlew assembleRelease` builds, not EAS builds.
**Fix:** Not needed — EAS Build manages release signing. Local Android builds are dev-only. The `android/` directory is gitignored and ephemeral.
**Status:** NOTED — EAS handles production signing. No action needed.

---

### P7-003 | HIGH | Android versionName mismatches app.json

**File:** `android/app/build.gradle` — `versionCode: 1, versionName: "0.1.0"` vs `app.json` — `version: "1.0.0"`

A local `./gradlew assembleRelease` would produce an APK with version 0.1.0 instead of 1.0.0.

**Impact:** Only affects local builds. EAS Build sources version from `eas.json` (`appVersionSource: "remote"`), so production builds are unaffected.
**Fix:** Not needed — same rationale as P7-002. Android dir is gitignored and regenerated.
**Status:** NOTED — EAS remote versioning is authoritative.

### P7-004 | HIGH | Supabase auth password settings are weak

**File:** `supabase/config.toml` (lines ~131-132)

```toml
minimum_password_length = 6
password_requirements = ""
```

Minimum 6 characters with no complexity requirements is below OWASP recommendations (8+ chars, mixed complexity). This affects local development only (production Supabase dashboard has separate settings), but the local config should match production intent and serves as documentation.

**Impact:** Weak passwords in local dev/seed data; config drift vs production.
**Fix:** Update to `minimum_password_length = 8` and add complexity requirements.
**Status:** FIXED

### P7-005 | MEDIUM | .env.local.example missing MAPBOX_DOWNLOAD_TOKEN

**File:** `.env.local.example`

The file documents 4 `EXPO_PUBLIC_*` variables but omits `MAPBOX_DOWNLOAD_TOKEN`, which is required for EAS native builds (referenced in `eas.json` production profile). Developers cloning the repo won't know they need this token until builds fail.

**Impact:** Failed EAS builds for new developers.
**Fix:** Add `MAPBOX_DOWNLOAD_TOKEN` with a comment explaining it's needed for native builds.
**Status:** FIXED

### P7-006 | MEDIUM | admin/.env.local.example hardcodes Supabase URL

**File:** `admin/.env.local.example`

```
NEXT_PUBLIC_SUPABASE_URL=https://tlggdherqjvybpddsqjj.supabase.co
```

The mobile `.env.local.example` uses `your-project-ref-here` as a placeholder, but the admin example hardcodes the real project URL. This is inconsistent and could confuse developers about whether to change it.

Note: The Supabase project ref is NOT a secret (it's in every client request), so this is a consistency issue, not a security issue.

**Impact:** Developer confusion; inconsistent documentation.
**Fix:** Use placeholder format consistent with mobile example.
**Status:** FIXED

### P7-007 | MEDIUM | No engines field in package.json

**File:** `package.json`

No `engines` field specifying the required Node.js version. The project requires Node 22 LTS (per AGENTS.md and docs/environment-setup.md), but nothing enforces this. Developers on Node 18 or 20 may encounter subtle issues.

**Impact:** Silent compatibility issues on wrong Node versions.
**Fix:** Add `engines` field.
**Status:** FIXED

### P7-008 | MEDIUM | No CI/CD pipelines exist

**Location:** `.github/workflows/` — directory does not exist

No GitHub Actions workflows for linting, type checking, testing, or deployment. The project has `npm run lint` and `npm run typecheck` scripts but no automation.

**Impact:** Regressions can be merged without automated checks.
**Fix:** Recommend adding at minimum: lint + typecheck on PR, EAS build on main push. This is a process gap, not a code fix.
**Status:** NOTED — Documented as CI/CD recommendation below.

### P7-010 | LOW | expo-splash-screen plugin not configured in app.json

**File:** `app.json`

`expo-splash-screen` is in dependencies (v55.0.15) but not listed in the `plugins` array in `app.json`. The splash screen works via the legacy `splash` config key, but the plugin provides more control (fade animation, duration, etc.).

**Impact:** Minor — splash works but without plugin-level customization.
**Fix:** Optional enhancement; current config is functional.
**Status:** NOTED — Working as-is.

---

### P7-011 | LOW | No deep link / universal link configuration

**File:** `app.json`

No `associatedDomains` (iOS) or `intentFilters` (Android) configured. The `scheme: "kanek"` enables `kanek://` custom scheme links, but universal links (`https://kanek.bz/...`) are not configured.

**Impact:** No web-to-app deep linking. Users can't share links that open the app directly.
**Fix:** Deferred — requires hosting an `apple-app-site-association` file and configuring `assetlinks.json`. Should be set up when a web domain is finalized.
**Status:** NOTED — Deferred to post-launch.

---

### P7-012 | LOW | Deno edge functions have no lockfile

**File:** `supabase/functions/deno.json`

No `deno.lock` file exists. The import map pins `@supabase/supabase-js` to `2.49.4`, but transitive dependencies are not locked. Builds could be non-reproducible if esm.sh CDN serves different transitive versions.

**Impact:** Potential non-reproducible edge function builds.
**Fix:** Generate with `deno cache --lock=deno.lock` in the functions directory. Low priority since Supabase deploys pin at build time.
**Status:** NOTED — Low risk, Supabase deployment snapshots dependencies.

### P7-013 | INFO | Supabase config: auth confirmations and secure_password_change disabled

**File:** `supabase/config.toml`

```toml
enable_confirmations = false
secure_password_change = false
```

These are local development settings. The production Supabase dashboard has separate controls. Documenting for awareness — production should enable email confirmations and secure password change.

**Status:** INFO — Verify production Supabase dashboard settings match security requirements.

Both `npm audit` (mobile) and `npm audit` (admin) report **zero vulnerabilities** across all severity levels. This is excellent.
